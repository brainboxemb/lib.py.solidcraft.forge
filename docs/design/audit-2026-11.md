# Forge foundational code audit — 2026-11

Status: **in progress**  
Audit baseline: `main` at `4ae39be50ab0fb45d033e472387839d129e6ef95`  
Research PR #178: retained as evidence only; **do not merge**

## Purpose

This audit answers a more fundamental question than "does the current model
render correctly?":

> Which parts of Forge are deliberate semantic contracts, and which parts only
> work because the compiler predicts or depends on incidental SolidCraft
> behaviour?

No production fix is accepted directly from the audit. Each confirmed finding
must first be reconciled with the architecture contract in
[forge-architecture.md](forge-architecture.md), then implemented as a small,
independently qualified change.

## Audit rules

1. Audit `main`, not an exploratory branch.
2. Separate public Forge semantics from native SolidCraft implementation
   details.
3. Mark every item as one of:
   - **CONFIRMED** — directly supported by current source/history/evidence;
   - **RISK / VERIFY** — plausible from source, but not yet proven end-to-end;
   - **DESIGN DECISION** — a rule that must be decided before implementation.
4. A passing render is not sufficient evidence.
5. A test that asserts an incidental native display name is not automatically a
   valid API contract.
6. Exploratory PR #178 may provide historical/native evidence, but its code is
   not a merge source.

## F-001 — Forge predicts SolidCraft-generated occurrence names

**Status: CONFIRMED**  
**Severity: critical**

Current assembly lowering contains:

```python
for index, instance in enumerate(instances, start=1):
    native_name = f"{component_name}:{index}"
    occurrence_names[id(instance)] = native_name
```

Forge then uses that predicted string for:

- `occurrence.move`;
- `joint.create`;
- `joint.as_built`;
- `joint.origin`;
- custom/topological joint references.

The semantic Python occurrence is therefore first tracked by Python object
identity and then converted into a name that Forge assumes SolidCraft will
generate.

This violates the object-first API design in `docs/05-cad-api-design.md`,
which says later relationships refer to the actual Python occurrence object
rather than to a generated SolidCraft label.

### Additional evidence

`run_script()` already rejects root component `placement=` with:

> root component placement requires the identity-aware occurrence executor;
> this foundational capability is not qualified yet

So the codebase already acknowledges that occurrence identity is a foundational
missing capability. The assembly compiler nevertheless predicts occurrence
names for other paths.

### Required direction

Forge needs an explicit occurrence-registration/identity layer. The eventual
native adapter must resolve a Forge occurrence identity to a native reference
without predicting browser numbering.

The exact SolidCraft 0.42 mechanism is still to be established from authoritative
command schemas. Do **not** invent the native mechanism in Forge.

## F-002 — Tests encode generated browser numbering as expected behaviour

**Status: CONFIRMED**  
**Severity: high**

`scpf/tests/test_assembly.py` contains at least 29 literal generated occurrence
names such as:

```text
Block:1
Block:2
Panel:2
Marker:1
Marker:2
```

Qualification tests also contain literal `Component:N` expectations.

Many of those tests combine two different concerns:

1. a useful semantic/native assertion, such as the joint frame or movement;
2. the accidental assumption that SolidCraft gave an occurrence one particular
   numbered browser name.

### Required direction

Split test responsibilities:

- semantic/IR tests identify occurrences by Forge identity;
- native adapter tests prove the registration mechanism;
- native qualification checks the resulting geometry, parameters,
  relationships and saved-design behaviour;
- only a SolidCraft-adapter compatibility test may care about a browser display
  name, and only when that display name itself is the subject of the test.

## F-003 — Grouping claims to be hierarchy-only, but compiler adds grounding

**Status: CONFIRMED**  
**Severity: high**

Public `ModelInstance.group()` says:

> Grouping changes hierarchy only. It does not align, attach or otherwise
> create a mechanical relationship.

`Assembly.group()` carries the same semantic promise.

Current `compile_assembly()` creates every named group with:

```python
component.create(..., grounded=True)
```

Grounding is mechanical solver state, not browser hierarchy.

Historical HUB75 evidence also shows a relevant behaviour change: a
`CornerBrackets` group that was historically ungrounded later became grounded
while its children were related to external side-board occurrences.

### Required direction

Hierarchy and mechanical grounding must be separate concepts in the internal
model and native adapter. Calling `.group()` must never silently add a
mechanical constraint.

The exact root/subassembly grounding policy is a separate design decision and
must be qualified independently.

## F-004 — `Assembly.group()` can leave attachment targets pointing at replaced objects

**Status: CONFIRMED BY SOURCE INSPECTION; native reproduction pending**  
**Severity: high**

`Assembly.group()` creates replacement instances:

```python
grouped = tuple(instance.group(name) for instance in self.instances)
```

It explicitly remaps assembly-owned anchor targets to those replacements.

It does **not** remap `Attachment.target` inside the replacement instances.

If an assembly already contains:

```python
child = Child().attach(parent)
assembly = (parent + child).group("Subassembly")
```

the grouped child can still carry an attachment whose target is the original
ungrouped parent object, while the assembly contains the replacement grouped
parent.

The compiler later requires the target object identity to exist in the
assembly, so this is internally inconsistent.

### Required direction

Any immutable transformation that replaces occurrence objects must remap the
complete relationship graph atomically, not just assembly-owned anchor
metadata.

## F-005 — Rotation support for attachment references is inconsistent

**Status: CONFIRMED**  
**Severity: high**

The compiler explicitly rejects several rotated-reference cases:

- direct `AnchorFrame` on an explicitly rotated occurrence;
- direct `AnchorTopology` on an explicitly rotated occurrence;
- corner anchors on an explicitly rotated occurrence.

However ordinary face anchors on a rotated occurrence are not rejected by
`_anchor_origin()`. Their world point is produced by adding only
`placement.position`; the occurrence rotation is not applied to the local
anchor point.

That creates a path that appears supported but is not fully transformed.

### Required direction

For every public attachment reference, Forge must do exactly one of:

1. correctly transform the complete frame/reference under occurrence
   Placement; or
2. reject the operation before command generation with a documented limitation.

There must be no partially transformed attachment path.

## F-006 — Script execution and package import expose different API names

**Status: CONFIRMED**  
**Severity: medium/high**

`scpf.__init__` publicly exports cardinal aliases including:

```text
TOP BOTTOM LEFT RIGHT FRONT BACK
```

The implicit namespace created by `run_script()` injects `Anchor`,
`AnchorFrame`, `X/Y/Z`, etc., but does not inject those cardinal aliases.

Therefore code can be valid as:

```python
from scpf import FRONT, BOTTOM
```

while the same names are unavailable in the implicit no-import SCPF script
language.

This mismatch was encountered directly while building the HUB75 diagnostic
fixture.

### Required direction

There is one public language. Either the implicit script namespace mirrors the
public package exports intentionally, or implicit injection is reduced to a
small documented prelude. The two surfaces must not drift.

## F-007 — Assembly lowering is a monolithic identity/hierarchy/solver adapter

**Status: CONFIRMED**  
**Severity: architectural**

`compile_assembly()` currently performs, in one function:

- definition deduplication and naming;
- parameter namespacing;
- group creation and grounding;
- component creation;
- copy creation;
- occurrence identity prediction;
- Placement lowering;
- custom-origin creation;
- anchor/topology conversion;
- joint creation;
- browser presentation state.

This makes it easy for a change in one concern (for example group hierarchy) to
change another concern (solver grounding) without a clear contract boundary.

### Required direction

Introduce explicit compiler stages/IR boundaries. See
`forge-architecture.md`.

## F-008 — Native SolidCraft 0.42 snapshot lacked compiler identity schemas

**Status: CONFIRMED; IDENTITY QUESTION NOW RESOLVED**  
**Severity: high documentation gap**

The original `docs/vendor/solidcraft/0.42.0/commands.md` records command IDs
but not the input/output schemas needed for compiler identity work.

The audit therefore introspected the pinned SolidCraft 0.42.0 executable
directly with `engine.describe`. The identity-relevant result is now recorded
in
[`docs/vendor/solidcraft/0.42.0/occurrence-identity.md`](../vendor/solidcraft/0.42.0/occurrence-identity.md).

Confirmed native contract:

- `component.create` returns the actual numeric occurrence id;
- `occurrence.copy` returns the new numeric occurrence id;
- later occurrence/joint/origin commands accept numeric occurrence ids;
- the copy command does not let Forge prescribe the future occurrence id.

This resolves the key architecture question: generated labels such as
`Component:2` are not required by SolidCraft and must not be used as Forge
identity. Identity-dependent replay requires runtime result binding or an
explicitly restricted static mode.

The remaining documentation task is to retain the full authoritative schemas,
not only this extracted identity summary.

## F-008a — Raw replay cannot safely express identity-dependent plans

**Status: CONFIRMED FROM SOLIDCRAFT 0.42 SCHEMAS**  
**Severity: critical architecture constraint**

SolidCraft creates the native occurrence id at runtime:

```text
component.create -> result.occurrence
occurrence.copy   -> result.occurrence
```

Later commands consume that id.

`occurrence.copy` does not accept a Forge-selected id for the new occurrence.
Therefore a static command document cannot know the correct selector for a
later move/joint/origin unless it guesses a generated name.

This is why historical PRs #166/#167 introduced logical result binding.

### Required architecture

- raw native command lists remain valid for plans with no runtime identity
  dependency;
- identity-dependent plans use a Forge execution document with logical
  references resolved from native command results;
- replay re-resolves those identities every time;
- generated browser labels are never the fallback.


## F-009 — Root occurrence Placement is explicitly blocked while assembly paths use unqualified identity assumptions

**Status: CONFIRMED**  
**Severity: high**

The runner refuses root component `placement=` until an
"identity-aware occurrence executor" exists.

At the same time `compile_assembly()` performs occurrence moves and joints by
predicting generated native names.

This is not a coherent capability boundary.

### Required direction

Occurrence identity must become a first-class compiler capability used
consistently by root and nested assemblies. After that, root Placement can be
qualified against the same mechanism instead of carrying a one-off blocker.

## F-010 — Component definition deduplication may omit build-affecting state

**Status: RISK / VERIFY**  
**Severity: potentially high**

`ModelDefinition.key` contains:

- class name;
- classified parameters;
- fixed numeric inputs;
- input bindings;
- anchors.

It does not include:

- the built `shape` itself;
- `external_parameters` directly;
- reference fields declared through the `field = None` mechanism.

This is only safe if every value capable of changing component geometry or
native behaviour is guaranteed to be represented in the key indirectly.

The runner intentionally supports non-parameter reference inputs. Their effect
on reusable definition identity has not yet been proven safe.

### Verification required

Construct focused cases where two instances of the same component class receive
different reference inputs and determine whether they can produce distinct
shape/native definitions while sharing the current key.

Do not change deduplication until that behaviour is understood.

## F-011 — Named semantic anchors and SolidCraft-generated names are different concerns

**Status: DESIGN CLARIFICATION**  
**Severity: important terminology**

Forge currently permits component-local named anchors. Resolving a user-defined
semantic name such as `"mount"` inside a component definition is not the same
problem as predicting SolidCraft browser names such as `"Bracket:2"`.

The audit must keep these concepts separate:

- **semantic name** — authored by the Forge model and owned by the Forge API;
- **Forge occurrence identity** — stable internal identity of a physical
  occurrence;
- **native reference** — SolidCraft-specific handle/reference used by commands;
- **native display/browser name** — presentation string generated or shown by
  SolidCraft.

The critical problem is depending on the last item as if it were the second or
third.

## F-012 — Attachment seed Placement and relationship semantics are mixed in one object mutation

**Status: RISK / DESIGN REVIEW**  
**Severity: medium/high**

`ModelInstance.attach()` immediately computes a concrete/symbolic translation
and replaces the child `placement`, while also storing an `Attachment`.

That means a semantic relationship and a native-solver seed pose are represented
through the same public occurrence state.

Historical evidence shows numeric seed moves can be valid and were present in
working models, so "make all seeds symbolic" is not a valid general fix.

### Design question

Should the semantic IR keep:

- declared Placement;
- attachment relationship;
- optional derived native seed pose

as three distinct concepts?

The architecture document currently says yes; implementation awaits the
remaining audit.

## F-013 — "first occurrence" has native-special meaning throughout lowering

**Status: CONFIRMED**  
**Severity: medium/high**

`compile_assembly()` repeatedly treats `instances[0]` specially for:

- definition creation;
- root grounding;
- copy creation;
- move ordering;
- component parent inference.

Some of this is forced by SolidCraft's component/occurrence model, but that
native constraint currently leaks directly into semantic compilation.

### Required direction

If SolidCraft requires one occurrence to arise implicitly from
`component.create`, isolate that fact in the native adapter. Forge semantic
identity must not mean "the first element in this Python list".

## F-014 — Normative change 0001 explicitly blesses generated occurrence labels

**Status: CONFIRMED**  
**Severity: critical documentation/design debt**

`docs/changes/0001-position-api-design.md` currently says:

> For occurrences, SolidCraft creates occurrence identity. Current replay-first
> Forge 0.42 lowering uses version-qualified labels such as `Board:1` /
> `Board:2` when a later fallback command must address the created occurrence.

It then calls that targeting rule a SolidCraft 0.42 backend contract.

This means the generated-name assumption is not merely an implementation leak:
it was promoted into normative design documentation.

The audit rejects that as a Forge architecture invariant. A display/generated
label may only be used if the authoritative SolidCraft schema proves it is the
stable programmable identity intended for replay. Browser observation is not
enough.

### Required direction

Do not silently edit historical change 0001 as if the old decision never
existed. A later foundational design change must explicitly supersede its
occurrence-identity section once the SolidCraft 0.42 schemas have established
the correct registration/reference mechanism.

## F-015 — Native unittest classes are not run against native evidence

**Status: CONFIRMED**  
**Severity: high qualification debt**

At least eleven files under `qualification/tests/` contain classes guarded by:

```python
@unittest.skipUnless(NATIVE_ROOT, "native SolidCraft evidence not supplied")
```

The workflow runs `qualification/tests` before creating native evidence and
without `NATIVE_ROOT`, so those classes are skipped.

After native evidence is produced, the workflow runs
`qualification/native_validation.py`; it does not rerun those unittest

Therefore the repository currently contains two native-validation styles:

1. native unittest code that looks active but is skipped in CI;
2. the actually executed centralized native validator.

This creates false confidence and allows stale assertions to survive.

## F-018 — Robust occurrence identity was implemented, then deliberately reverted

**Status: CONFIRMED BY PR HISTORY**  
**Severity: critical process/design finding**

PR #166 introduced a Forge execution document with logical `$ref` bindings.
PR #167 then integrated those handles into assembly lowering:

- every Forge occurrence received a logical handle such as
  `occurrence:0`;
- `component.create` / `occurrence.copy` result fields were bound to those
  handles;
- later `occurrence.move`, `joint.origin`, `joint.create` and
  `joint.as_built` used the logical reference;
- generated strings such as `Board:1` remained only human-readable labels.

That work was subsequently reverted by PR #170. The stated reason was not that
logical identity was incorrect, but that runtime result binding required Forge
to remain in the execution loop and therefore changed the normal output from a
raw independently replayable SolidCraft command list into a Forge execution
document.

Release 0.3.0 then explicitly deferred result-handle execution to roadmap issue
#168 and restored predicted native labels.

### Consequence

The current identity problem is a known architectural trade-off, not an unknown
implementation accident.

The audit has closed #168 as optional roadmap work. Reliable occurrence identity
is foundational and must be resolved before treating the current assembly
compiler as a stable base.

### What is not yet decided

Do **not** automatically restore PR #166/#167.

Those PRs prove that a Forge-owned logical identity layer is feasible, but they
were not the final native-qualified answer. The audit must first determine from
SolidCraft 0.42 authoritative schemas whether a replay-first mechanism exists
that avoids runtime barriers. If not, the project must explicitly choose
between:

1. a Forge execution document with runtime result binding; or
2. accepting a restricted static/replay mode that rejects models requiring
   unresolved runtime occurrence identity.

Predicting browser labels is not an acceptable third option.



## F-019 — Normative Sketch centring contract is not implemented

**Status: CONFIRMED**  
**Severity: high public-API drift**

The normative API design says:

```python
sketch.add(profile, anchor=CENTER)
```

and explicitly states that `CENTER` is the default semantic centring operation,
while numeric `offset=(-width/2, -depth/2)` used only to emulate centring is a
smell.

Current `Sketch.add()` has the signature:

```python
add(profile, *, offset=(0, 0))
```

and its own docstring says:

> Semantic 2D anchor placement is not implemented by this method yet.

The implementation therefore places a rectangle from its sketch-local origin
toward positive coordinates unless the caller manually offsets it.

Current tests lock in that experimental behaviour:

- a 40×30 standalone Rectangle2D is expected to emit p1 `[40, 30]`;
- attached sketch examples use `offset=(-20, -15)` to centre a 40×30
  rectangle.

That is the exact workaround the normative design says should not be necessary.

### Required direction

Choose the normative design deliberately. If semantic profile anchoring remains
the intended API, implement and qualify it and migrate tests/examples away from
manual centring offsets. Do not change the design document to bless the
experimental behaviour merely because tests currently encode it.

## F-020 — Reusable-definition key omits inherited parameter values

**Status: CONFIRMED BY SOURCE INSPECTION**  
**Severity: high**

`ModelDefinition.key` includes:

- class name;
- local published parameters;
- fixed inputs;
- input bindings;
- anchors.

It explicitly omits `external_parameters`.

For a parent-derived child input, `_parameter_input()` records for example:

```text
input binding:       width -> shared_width
external parameter:  shared_width = 40
```

Two child occurrences can therefore have the same key when both bind
`width -> shared_width`, even if one receives
`Parameter("shared_width", 40)` and the other receives
`Parameter("shared_width", 60)`.

`compile_assembly()` groups by that key and then compiles only
`instances[0].definition`. The second definition's different
`external_parameters` value is no longer examined by that path, so the
intended conflict can be hidden by deduplication.

### Required direction

Definition identity must include every build/dependency input whose difference
can change native definition semantics. At minimum the external parameter
contract must participate in deduplication or be validated across every
occurrence before sharing a definition.

This should be fixed as part of a general DefinitionSpec design rather than by
adding one more tuple member without auditing all build-affecting state.



## F-021 — Parameter publication can falsely imply native associativity

**Status: CONFIRMED BY SOURCE INSPECTION**  
**Severity: critical**

Forge currently has two separate mechanisms:

1. `_collect(shape)` finds every Parameter/Expression still present anywhere
   in the semantic Shape tree and emits `parameters.add`;
2. feature lowering may later call `pv()` and emit a concrete number instead
   of a native expression.

`_warn_missing_model_parameters()` largely checks whether the declared
parameter name appears in the emitted `parameters.add` set. It does not build
a dependency graph from parameter to every native use.

Therefore a parameter can exist in the SolidCraft parameter table while one of
its geometry uses has already been flattened.

### Concrete source paths

Examples include:

- explicit Sketch custom plane origin:
  `plane={"origin": [pv(v) for v in sketch_origin], ...}`;
- an explicitly positioned non-directional native Hole:
  `position=[pv(v) for v in at]`;
- `Shape.move()`, which converts its XYZ arguments with `pv()` before the
  Shape node is stored.

For the first two, the original Parameter may still remain elsewhere in the
Shape tree, so `_collect()` can publish it even though the emitted coordinate
is numeric.

### Failure mode

A saved SolidCraft document can show an editable parameter and update some
dependent geometry, while a numerically flattened pick/origin remains at the
old value. Forge may emit no warning.

That is the same class of failure the project is trying to prevent with Q5
saved-design mutation tests.

### Required direction

Associativity validation must be based on actual emitted dependencies, not on
parameter publication alone.

The compiler/IR should distinguish:

- declared/public parameter;
- native parameter definition;
- every native expression/reference that depends on it;
- intentional authoring-time numeric pick used only to select stable topology;
- accidental value flattening that changes geometric behaviour.

A numeric topology pick may be legitimate when SolidCraft persists the selected
topology associatively; that must be proven by native qualification rather than
treated the same as an arbitrary flattened coordinate.



## F-022 — Feature-reference associativity is only partially qualified

**Status: CONFIRMED COVERAGE GAP**  
**Severity: medium/high**

Within-component feature anchoring is deliberately more associative than a raw
XYZ placement for supported rectangular faces. `_anchored_features()` emits
two native edge references for the supported top/bottom rectangular case and
uses numeric coordinates only as topology picks.

That is a reasonable design.

However the main `anchored-holes` qualification case explicitly states:

> No saved-design mutation in this fixture; geometry and feature placement are
> measured at Q4.

Therefore the current qualification proves the holes are initially in the right
place, but does not prove the claimed native references survive a parameter
change in the saved SolidCraft design.

There are also deliberate fallback paths with no stable native references, for
example a Hole placed on the joined circular top of a boss. Those paths fall
back to numeric authoring coordinates.

### Required direction

Classify feature-placement capabilities explicitly:

- **associative reference-backed** — requires Q5 mutation evidence;
- **authoring-time numeric placement** — must be documented as non-associative,
  or rejected when a public parameter would imply a persistent dependency;
- **unsupported** — reject before lowering.

A Q4 render alone must not promote a relationship to "associative".

## F-023 — Release 0.3.0 knowingly shipped around an unresolved foundational identity gap

**Status: CONFIRMED BY CHANGELOG/PR HISTORY**  
**Severity: process failure**

Release 0.2.0 was withdrawn because:

> Forge's foundational create/place/copy/attach model, occurrence identity
> strategy and replay contract were not fully designed and qualified.

PRs #166/#167 then implemented a logical runtime identity mechanism.

PR #170 reverted that mechanism to preserve raw replay-first output.

Release 0.3.0 subsequently:

- introduced `Placement` as the foundational occurrence API;
- explicitly deferred runtime result-handle execution to roadmap #168;
- restored generated-label targeting for identity-dependent fallback commands.

The project therefore resumed release progression while one of the reasons for
withdrawing 0.2.0 — reliable occurrence identity — remained unresolved.

### Required process correction

A withdrawn foundational capability cannot be converted into a roadmap item
merely to unblock the next release.

The release gate needs explicit **architecture blockers** in addition to green
tests. A known blocker may only be cleared by:

1. a qualified implementation; or
2. narrowing/rejecting the public capability so the unresolved path is no
   longer claimed as supported.



## F-024 — Dataclass component definition identity ignores non-numeric build inputs

**Status: CONFIRMED BY SOURCE INSPECTION**  
**Severity: critical for reusable definition correctness**

The runner deliberately supports dataclass model classes. It instantiates the
dataclass with all constructor arguments:

```python
instance = cls(*args, **kwargs)
```

but `_parameterized_instance()` only records an argument in
`parameters`, `fixed_inputs`, `external_parameters` or
`input_bindings` when the value is one of:

```python
int, float, Parameter, Expression
```

Booleans are explicitly excluded and strings/enums/other values are skipped.

`ModelDefinition.key` then uses only the classified metadata and anchors; it
does not include the built Shape.

Therefore two instances of the same dataclass component can execute different
`build()` branches or produce different physical geometry/material/feature
intent from a non-numeric field while still receiving the same reusable
definition key.

Examples of unsafe input categories include:

- `mirrored: bool`;
- `material: str`;
- an enum selecting a profile/variant;
- any other dataclass field used by `build()`.

The compiler groups by that key and compiles only the first definition.

### Required direction

Definition identity cannot be derived from "numeric parameters only".

The semantic DefinitionSpec must retain every build-affecting input, with an
explicit classification such as:

- native numeric parameter/dependency;
- fixed numeric build input;
- fixed non-numeric build input;
- external object/reference input;
- occurrence-only metadata.

Values that cannot be compared/serialized safely for definition sharing should
either get an explicit identity token or force separate definitions.

No architecture-changing production PR should be merged until:

1. this audit is complete;
2. the architecture invariants are agreed;
3. relevant SolidCraft 0.42 native schemas are locally archived;
4. each implementation change has one narrow responsibility;
5. tests are rewritten to assert Forge semantics rather than accidental native
   numbering.
