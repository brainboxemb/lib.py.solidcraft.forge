# SolidCraft execution and occurrence identity

Status: **design in progress; blocks release**

This document records the SolidCraft 0.42 capabilities relevant to reusable
occurrence placement and the resulting Forge compiler constraints.

## 1. Native capabilities verified in SolidCraft 0.42

### component.create

Creates a component and its first occurrence.

Relevant facts:

- Forge can choose the component name.
- The command returns a numeric component id.
- The command returns the first occurrence id.
- It does not accept an occurrence placement/translate parameter.
- The occurrence display name is generated by SolidCraft.

### occurrence.copy

Creates another occurrence of a shared definition.

Relevant facts:

- accepts a component id/name or occurrence;
- returns the new numeric occurrence id;
- accepts numeric `translate=[x,y,z]` during creation;
- that translate is numeric-only in SolidCraft 0.42.

This is the preferred lowering for a concrete initial placement of an extra
occurrence.

### occurrence.move

Moves one existing occurrence.

Relevant facts:

- it needs a specific occurrence id/name;
- translation may contain length expressions;
- expression moves remain associated with parameters after save/reopen and
  `parameters.change`.

This is a capability for an already identified occurrence. It is not the
default meaning of Forge `move()`.

## 2. Identity

SolidCraft command results provide numeric occurrence ids. Exact placement paths
are lists of occurrence ids.

SolidCraft also has generated display names such as:

```text
Board:1
Board:2
```

Those names are labels. Forge does not create or control them.

Therefore this is forbidden compiler logic:

```python
native_name = f"{component_name}:{index}"
```

when the string is later used as if it were authoritative occurrence identity.

It may be useful for diagnostics or expected UI labels, but not as the
foundation of dependent commands.

## 3. Current static-batch limitation

Current Forge `--connect` compiles the entire model to one native
`commands[]` list and sends it through one SolidCraft `engine.batch`.

Current replay does the same.

SolidCraft 0.42 `engine.batch` returns a `results[]` entry for every completed
step. Forge's current `live.py` only checks `completed` / `failed` and does
not retain those step results.

A static batch has no verified in-batch Forge-level variable binding such as:

```text
@right = result(occurrence.copy).occurrence
occurrence.move occurrence=@right
```

No SolidCraft 0.42 mechanism has been verified that substitutes a result from
step N into the parameters of step N+1 inside the same batch.

Therefore commands that depend on a newly created id require an execution
barrier: run the creation phase, read the returned `results[]`, bind logical
Forge handles to the returned ids/paths, then execute the dependent phase.

## 4. Required Forge execution model

Forge should compile to a semantic plan with logical occurrence handles.

Conceptually:

```text
create definition Block
create first occurrence -> @left
copy Block at numeric placement -> @right
attach @marker to @right
```

The executor resolves logical handles to actual SolidCraft ids/paths from
command results.

For live/connect execution this can use **phased batches**, not necessarily one
network call per CAD command:

```text
batch A: definitions + occurrence creation
    -> results[] supplies actual occurrence ids
resolve Forge logical handles
batch B: dependent placement / anchors / attachments
```

Replay must perform the same handle-resolution phases from the Forge semantic
plan, not replace handles with predicted display labels.

The precise serialized plan format is still to be designed and qualified.

## 5. Creation-time placement rule

When the final Placement of an extra occurrence is concrete and SolidCraft can
represent it at creation time:

```text
Forge Placement
    -> occurrence.copy(..., translate=[...])
```

Do not emit:

```text
occurrence.copy(...)
occurrence.move("Board:2", ...)
```

The second form creates an unnecessary identity dependency.

## 6. Parameter-driven placement

SolidCraft 0.42 cannot store a parameter expression in
`occurrence.copy.translate`.

A parameter-driven Placement therefore needs:

1. the actual occurrence id/path returned from creation;
2. an expression-capable native placement operation such as
   `occurrence.move`;
3. saved-design mutation qualification.

This is why parameter-driven placement and numeric creation-time placement are
separate capabilities.

## 7. Rejected fallbacks

### Predict generated occurrence labels

Rejected. Forge does not own `Board:2`.

### Predict numeric ids

Rejected. Runtime ids are SolidCraft-owned state.

### Convert placement into planar joints

Rejected. A joint is an assembly relationship, not occurrence placement.

A planar-joint lowering was introduced in Forge on 2026-11-14 as an
implementation workaround for an assumed SolidCraft 0.30.1 capability gap.
It was not an approved API design decision and must not be used as precedent.

### Ground a parameter-driven occurrence

Rejected as a general solution. SolidCraft 0.42 deliberately prevents grounded
occurrences from following expressed moves.

## 8. Qualification requirements

At minimum the qualification suite must inspect:

- generated command/semantic plan;
- resulting native occurrence count and shared definitions;
- exact native positions;
- saved design after parameter mutation;
- native joint list;
- replay behavior;
- absence of generated placement joints;
- absence of generated-label identity dependencies in the Forge plan.
